# 읽기 판단 재설계: 땜질 제거

- 날짜: 2026-10-14
- 질문: 요청을 어느 자료에서 읽을지 정하는 판단을, 실패 사례마다 덧댄 보정 없이 판단 구조만으로 정확하게 만들 수 있는가?
- 원본 결과: [`read-decision-redesign-runs/`](read-decision-redesign-runs/) (Jev, 설정마다 3회)
- 관련: [Jev vs Codex 비교](jev-vs-codex-decision.md), [케이스 목록](decision-benchmark-cases.md)

- **원래 코드보다 확실히 좋아졌습니다.** v3에서 재설계만 맞힌 케이스 12건, 원래 코드만 맞힌 케이스 3건입니다(McNemar p = 0.035).

- **잘못된 실행이 사라졌습니다.** 다른 자료를 읽거나 되물어야 할 때 바로 실행한 경우가 23건에서 0건이 됐습니다. 남은 실패는 모두 되묻기나 멈춤 같은 안전한 쪽입니다.
- 판단 호출이 요청당 0.4번 늘어 p95가 0.2초 늘었습니다. 후보가 줄어든 덕분에 토큰과 비용은 조금 줄었습니다.

## 무엇이 땜질이었나

| 땜질 | 어디서 왔나 | 바꾼 것 |
|---|---|---|
| DB 테이블마다 join 변형을 후보로 따로 둠 (`orders`, `orders + customers`, …) | join 질문을 표현하려고 | 테이블 하나 = 후보 하나. 연결된 테이블은 `relations`로 붙여 두고 따로 묻는다 |
| 고른 조회를 하나로 합치기 (`coveringRdbRead`) | 겹친 join 변형을 정리하려고 | 삭제 |
| "어느 테이블의 행인가" 추가 질문 (`selectRowTable`, #327) | 합치기가 `orders`로 쏠려서 | 삭제. 아래 `record_read`가 대신한다 |
| 주 조회 고르기 + "출처가 겹치나" 질문 (예시가 평가 문장) | 여러 조회 중 하나를 고르려고 | 단계별 질문으로 다시 짬 |
| 이름 붙은 도구 기준 0.3, 그 옆 조회 기준 0.8 | Slack 발송 0.49 사례, 8월 주문내역 사례 | 기준은 모두 0.5. "요청이 이 도구를 직접 말함"을 Jev에 근거로 준다(`named_in_request`) |
| 표현(정규식)으로 Jev 결정 뒤집기 2곳 | 이전 표 후속 질문 사례 | 삭제. 같은 표현 단서는 원래대로 Jev에 근거로만 간다 |
| 프롬프트 예시가 평가 문장과 같거나 거의 같음 | 실패 사례를 예시로 넣으면서 | 원칙 문장과 평가와 겹치지 않는 예시로 바꿈. 다시 들어오지 않게 테스트 추가(`prompt-leak.test.ts`) |
| 어휘 점수 정렬 (`rankReadHintsByRelevance`, 스키마 -50점) | 선택지 순서용 | 쓰는 곳이 없어져 삭제 |

## 새 구조

첫 판단은 그대로입니다. 경로와 후보마다 "필요한가"를 각각 묻습니다. 고른 조회가 둘 이상이면 서로 의존하는 순서대로 사실을 묻고, 결과는 정해진 규칙 하나로 나옵니다([`read-decision.ts`](../../packages/core/src/intelligence/commands/chat/routing/read-decision.ts)).

1. **어느 조회의 행이 요청의 레코드인가** (`record_read`, 하나 고르기)
   - 상품 목록은 products의 행이고, 지역별 매출은 orders의 행입니다(고객 지역은 각 주문에 붙이는 relation).
   - 하나 고르기로 물어 후보끼리 비교하게 합니다. 처음에 후보마다 예/아니오로 물었을 때는 느슨하게 관련된 조회도 0.5~0.7을 받았습니다.
2. **여러 곳의 자료를 합치거나 비교하라는가** (`combine_sources`, 서로 다른 곳이 있을 때만)
   - 한 DB 안의 테이블은 합치기가 아니라 relation입니다. "캠페인별 광고비"를 합치기로 잘못 본 사례가 있어 이렇게 정했습니다.
3. **relation마다 그 열이 필요한가** (`attach_N_M`)
   - "어떤 레코드"와 "어떤 열"이 서로 경쟁하지 않습니다. 계획을 세우는 경로(반복 업무, 1회 실행)도 같은 질문으로 join을 정합니다.
4. 고른 조회 말고 다른 곳의 조회가 있으면, 고른 것을 기준으로 다시 묻습니다.
   - **다른 곳에도 같은 종류의 레코드가 있는가** (`same_records_elsewhere`)
   - **곳마다: 요청이 이곳을 가리키는가** (`points_to_place_N`, 이전 선택 포함)
   - "같은 레코드"는 레코드가 정해진 뒤에야 뜻이 있어서 선택 다음에 묻습니다. 모든 조회를 한꺼번에 놓고 물었을 때는 대부분의 요청을 모호하다고 답했습니다.

**규칙**
- 합치기 → 모두 계획합니다.
- 가리키는 곳이 정확히 하나 → 그곳의 조회를 씁니다.
  - ERP처럼 DB와 API가 같은 이름을 쓰면 둘 다 가리키므로 하나가 아닙니다.
- 같은 종류가 다른 곳에도 있고 가리키는 곳이 없음 → 되묻습니다.
- 그 밖 → 고른 조회를 읽습니다.
- 모든 판단 기준은 "가능성이 더 높음"(0.5) 하나입니다.

## 과정에서 확인한 것

- **예전 질문의 정확도 일부는 평가 문장 예시 덕분이었습니다.** 예시를 원칙 문장으로 바꾸자 "출처가 겹치나" 질문의 정확도가 떨어졌고, 질문 구조를 바꿔서 되찾았습니다.
- **두 사실을 한 문장에 묶은 질문은 0.5 근처로 답했습니다.** 예: "다른 곳에도 있고, 요청이 어느 곳인지 말하지 않는다". 사실 하나씩 묻자 답이 갈렸습니다.
- **어휘 근거를 붙였다가 뺐습니다.** "곳 이름의 단어가 요청에 있음"을 근거로 붙여 봤습니다. 그런데 "주문 API"처럼 곳 이름에 자료 이름이 들어 있어 "주문 목록 보여줘"가 주문 API를 가리킨다고 판단됐습니다. 그래서 뺐습니다.
- **도구 이름 근거는 남겼습니다.** 예전에 0.49로 실행되지 않던 "#ax테스트에 … 보내줘"가 `named_in_request` 근거만으로 0.86~0.91이 됐습니다. 스프레드시트 파일 이름 근거는 단위 테스트로만 확인했고, 실제 Jev 호출로는 확인하지 못했습니다.

## 공정성

- **개발 세트는 고치면서 계속 봤습니다.** 구조를 6번 바꿔 가며 쟀습니다. 그래서 개발 세트 94.8%는 낙관적인 수치입니다.
- **v3는 블라인드입니다.**
  - 재설계를 시작하기 전에, 결과를 보지 않은 별도 작성자(에이전트)가 쓰고 별도 검토자가 확인했습니다(수정 0건).
  - 엔진을 돌리기 전에 커밋했습니다(#328).
  - 재설계 작업자는 케이스 내용을 열어 보지 않았고, 전체 통과율만 봤습니다.
  - 재설계 결과는 마지막에 한 번만 쟀습니다.
  - 원래 코드와 #327 코드는 같은 v3로 비교용으로 쟀습니다.
- **v3 결과로는 아무것도 고치지 않았습니다.** 다음 수정의 효과는 새 블라인드 세트로 재야 합니다.

## 남은 실패 (개발 세트)

- **자료가 한 곳인데 되묻기 (scale)**
  - 해당 케이스: hs-unpaid-invoices, hs-survey-average, h2s-support-agents
  - "고객지원 만족도", "고객지원 상담원"처럼 곳 이름(고객지원 DB)이 요청에 들어 있는데, 요청이 그곳을 가리킨다는 확률이 0.5 근처에 머뭅니다.
- **첫 판단에서 아무 조회도 고르지 않음:** 가끔 생깁니다. 예: "가입한 고객 이메일 목록", 후보마다 0.5 근처.
- **이전 표 후속:** "이거 지역별로 금액 합쳐줘"가 가끔 `uncertain`으로 끝납니다.
- **모든 엔진 공통:** Slack 검색어를 요청에서 채우지 않는 문제(h-slack-search)는 그대로입니다.
