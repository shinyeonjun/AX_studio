## 정정 (2026-10-14 저녁)

처음 올린 이 문서(#329)에는 틀린 주장이 두 개 있었습니다. 외부 검토에서 지적받아 다시 확인했습니다.

- **"원래 코드보다 확실히 좋아졌다"는 철회합니다.**
  - 처음 v3 수치(94.3%)는 커밋하기 전 작업 상태에서 잰 것입니다.
  - 고정 커밋(`4f4dfede`)에서 다시 재니 92.1%이고, 원래 코드와의 차이는 p = 0.077로 유의하지 않습니다.
- **"엉뚱한 실행이 사라졌다"는 철회합니다.**
  - 23 → 0은 개발 세트 숫자입니다.
  - 블라인드 v3에서는 원래 코드 20건, #327 0건, 재설계 9건입니다.
- 커밋 전 측정은 지우지 않고 [`v3-redesign-unpinned/`](read-decision-redesign-runs/v3-redesign-unpinned/)에 남겼습니다. 두 측정 사이에 바뀐 코드는 테스트·문서와 타입 표기뿐이지만, 결과 파일만으로는 이를 증명할 수 없습니다.

## 무엇을 재나: 라우팅 정확도

이 문서의 "정확도"는 **라우팅 정확도**입니다. 값까지 맞는지는 보지 않습니다.

- 채점하는 것: 결과 종류(실행·되묻기·답변 등), 경로, 출처 선택지, 도구, 지정된 테이블·연결·경로, 빠진 join, 변환 종류
- 채점하지 않는 것: 필터 값, 정렬 기준, 개수, 불필요하게 더 붙인 join
- v3 76건 중 10건은 실행과 되묻기를 모두 정답으로 받습니다.

| 땜질 | 어디서 왔나 | 바꾼 것 |

## 새 구조

첫 판단은 그대로입니다. 경로와 후보마다 "필요한가"를 각각 묻습니다. 고른 조회가 둘 이상이면 서로 의존하는 순서대로 사실을 묻고, 결과는 정해진 규칙 하나로 나옵니다([`read-decision.ts`](../../packages/core/src/intelligence/commands/chat/routing/read-decision.ts)).

1. **어느 조회의 행이 요청의 레코드인가** (`record_read`, 하나 고르기)
   - 상품 목록은 products의 행이고, 지역별 매출은 orders의 행입니다(고객 지역은 각 주문에 붙이는 relation).
   - 하나 고르기로 물어 후보끼리 비교하게 합니다. 처음에 후보마다 예/아니오로 물었을 때는 느슨하게 관련된 조회도 0.5~0.7을 받았습니다.
2. **여러 곳의 자료를 합치거나 비교하라는가** (`combine_sources`, 서로 다른 곳이 있을 때만)
   - 한 DB 안의 테이블은 합치기가 아니라 relation입니다. "캠페인별 광고비"를 합치기로 잘못 본 사례가 있어 이렇게 정했습니다.
3. **relation마다 그 열이 필요한가** (`attach_N_M`)
   - "어떤 레코드"와 "어떤 열"이 서로 경쟁하지 않습니다. 계획을 세우는 경로(반복 업무, 1회 실행)도 같은 질문으로 join을 정합니다.
4. 고른 조회 말고 다른 곳의 조회가 있으면, 고른 것을 기준으로 다시 묻습니다.
   - **다른 곳에도 같은 종류의 레코드가 있는가** (`same_records_elsewhere`)
   - **곳마다: 요청이 이곳을 가리키는가** (`points_to_place_N`, 이전 선택 포함)
   - "같은 레코드"는 레코드가 정해진 뒤에야 뜻이 있어서 선택 다음에 묻습니다. 모든 조회를 한꺼번에 놓고 물었을 때는 대부분의 요청을 모호하다고 답했습니다.

**규칙**
- 합치기 → 모두 계획합니다.
- 가리키는 곳이 정확히 하나 → 그곳의 조회를 씁니다.
  - ERP처럼 DB와 API가 같은 이름을 쓰면 둘 다 가리키므로 하나가 아닙니다.
- 같은 종류가 다른 곳에도 있고 가리키는 곳이 없음 → 되묻습니다.
- 그 밖 → 고른 조회를 읽습니다.
- 모든 판단 기준은 "가능성이 더 높음"(0.5) 하나입니다.

## 과정에서 확인한 것

- **예전 질문의 정확도 일부는 평가 문장 예시 덕분이었습니다.** 예시를 원칙 문장으로 바꾸자 "출처가 겹치나" 질문의 정확도가 떨어졌고, 질문 구조를 바꿔서 되찾았습니다.
- **두 사실을 한 문장에 묶은 질문은 0.5 근처로 답했습니다.** 예: "다른 곳에도 있고, 요청이 어느 곳인지 말하지 않는다". 사실 하나씩 묻자 답이 갈렸습니다.
- **어휘 근거를 붙였다가 뺐습니다.** "곳 이름의 단어가 요청에 있음"을 근거로 붙여 봤습니다. 그런데 "주문 API"처럼 곳 이름에 자료 이름이 들어 있어 "주문 목록 보여줘"가 주문 API를 가리킨다고 판단됐습니다. 그래서 뺐습니다.
- **도구 이름 근거는 남겼습니다.** 예전에 0.49로 실행되지 않던 "#ax테스트에 … 보내줘"가 `named_in_request` 근거만으로 0.86~0.91이 됐습니다. 스프레드시트 파일 이름 근거는 단위 테스트로만 확인했고, 실제 Jev 호출로는 확인하지 못했습니다.

## 공정성

- **개발 세트는 고치면서 계속 봤습니다.** 구조를 6번 바꿔 가며 쟀습니다. 그래서 개발 세트 94.8%는 낙관적인 수치입니다.
- **v3는 블라인드입니다.**
  - 재설계를 시작하기 전에, 결과를 보지 않은 별도 작성자(에이전트)가 쓰고 별도 검토자가 확인했습니다(수정 0건).
  - 엔진을 돌리기 전에 커밋했습니다(#328).
  - 재설계 작업자는 케이스 내용을 열어 보지 않았습니다.
  - 다만 재설계하는 동안 **원래 코드와 #327의 v3 전체 통과율(83.3%, 92.5%)은 알고 있었습니다.**
  - 재설계 결과로 v3를 잰 것은 끝난 뒤 한 번(커밋 전)과, 검토 지적 뒤 고정 커밋 재측정 한 번입니다. 두 측정 사이에 코드를 고치지 않았습니다.
- **v3 결과로는 아무것도 고치지 않았습니다.** 아래 v3 실패를 고친다면 그 효과는 새 블라인드 세트(v4)로 재야 합니다.
