1. 현재 전체 구조

AX Studio의 “백엔드”는 인터넷에 있는 별도 서버가 아닙니다. Electron의 권한 있는 Main 프로세스와 Core가 백엔드 역할을 합니다. 화면은 직접 DB·파일·토큰을 만지지 않고, 정해진 명령만 호출합니다.

프로그램 내부 경계 로컬 디스크 업무 탐색/네트워크 비밀 데이터는 별도 보관
1

예시 접수

PDF, CSV, XLSX 결과물을 고르고 “다음부터 반복해줘”라고 말합니다.

ax:importArtifact
2

명령 통과

UI가 직접 DB를 만지지 않고 AX command 하나를 호출합니다.

discovery.start
3

결과 관찰

결과물 안의 숫자·필드·표를 관찰값으로 바꿉니다.

OutputObservation
4

자료 탐색

연결된 파일·시트·SQLite를 제한된 읽기로 살펴봅니다.

DiscoverySourceProvider
5

재현 검증

여러 예시에서 같은 결과가 나오는 후보만 남깁니다.

6

업무화

통과한 blueprint를 WorkflowIR로 저장하고 기존 Runtime에 맡깁니다.

publish → execute

2. Work Discovery가 하는 일

Work Discovery는 AI가 마음대로 코드를 만드는 기능이 아닙니다. 제한된 자료 읽기와 정해진 변환식으로 “이 결과를 어떻게 만들었는가”를 찾아보고, 과거 예시로 다시 계산해본 뒤에만 업무로 저장합니다.

collecting_examples예시 접수
observing_output결과물 항목 추출
inventory_sources자료 종류 목록화
exploring_sources제한된 자료 읽기
synthesizing후보 변환식 생성
validating모든 예시로 검증
needs_clarification모호한 후보 질문
ready_to_publish저장 가능
publishingWorkflowIR 컴파일
publishedworkflow 연결 완료
failed필수 결과 재현 실패
cancelled사용자 취소
상태 전이는 코드에 고정되어 있습니다. 예를 들어 validating → ready_to_publish가 되려면 필수 관찰값이 후보에 모두 매핑되어야 하고, 질문이 남아 있으면 publish할 수 없습니다.

구체적인 예: 월간 보고서

1
입력월간보고서.pdf와 “매달 같은 보고서를 만들어줘”를 받습니다.
2
관찰PDF에서 “총매출: 12.4억”, “달성률: 84%” 같은 숫자를 찾습니다.
3
탐색연결된 sales.xlsx, local folder, SQLite 테이블을 목록화하고 일부만 읽습니다.
4
후보 생성SUM(sales.amount), 행 개수, 실제값/목표값 비율 같은 제한된 후보를 만듭니다.
5
재현과거 예시마다 계산 결과가 원본 숫자와 맞는지 비교합니다.
6
업무화모든 필수 필드가 통과하면 읽기 step과 transform step이 있는 workflow로 컴파일합니다.

지금의 후보 수학

현재 deterministic path의 중심은 TransformExpr입니다. 임의의 JavaScript나 SQL이 아니라 아래처럼 제한된 표현식만 평가합니다.

{
  "op": "aggregate",
  "input": {
    "op": "source",
    "sourceId": "sheet:C:\\data\\sales.xlsx"
  },
  "fn": "sum",
  "column": "amount"
}

지원 예: source, column, filter, aggregate(count/sum/avg/min/max), ratio, lookup, select, sort, limit

즉 현재 기능은 “범용 AI 프로그램 합성”이 아니라 반복 사무업무에 맞춘 작은 변환 언어입니다. 이 제한이 안전성과 재현성의 핵심입니다.

3. AI와 화면은 무엇을 직접 할 수 있는가?

이번 구조 개편의 중요한 변화는 AxCommandService가 AI가 보는 단일 제어면이 된 것입니다. AI는 DB query나 shell command를 고르는 대신, 등록된 명령 이름과 인자만 요청합니다.

명령의 예

명령역할
source.list연결된 자료 목록 보기
source.file.read허용된 로컬 폴더 안의 제한된 파일 읽기
capability.invokecatalog에 등록된 읽기 capability 실행
workflow.create/update검증된 WorkflowIR 저장·버전 생성
discovery.start/publish예시 기반 업무 발견 시작·workflow로 저장
workflow.run저장된 workflow를 Runtime으로 실행

Host와 Agent의 차이

발신자허용되는 것
Host / Rendererread, present 중심. UI가 실수로 workflow/run 권한을 얻지 않도록 제한
Agent context정의된 workflow·discovery·ephemeral 명령을 요청할 수 있지만, 각 schema/catalog/contract 검증을 통과해야 함
모델 자체임의 shell, unrestricted SQL, arbitrary filesystem, connector method를 직접 호출하지 않음
이 경계는 “AI가 똑똑하니까 믿는다”가 아니라, AI가 틀려도 요청 가능한 행동의 종류와 인자를 코드가 제한한다는 의미입니다.

4. 코드 구조: 계약 → 카탈로그 → 모듈 → Workflow → Runtime

contracts

Zod schema와 중립 타입입니다. TableArtifact, DocumentArtifact, FileRef, capability I/O 같은 공용 약속입니다.

catalog

“무엇을 할 수 있는가”의 목록입니다. connector 구현을 직접 실행하지 않고 capability, side effect, 입력·출력 계약을 제공합니다.

modules

Gmail, Slack, local folder/sheet, RDB, document, HTTP, webhook, transform의 실제 구현입니다. 모듈끼리 서로 직접 알지 않습니다.

workflow/canvas

자연어·캔버스 초안을 실행 가능한 WorkflowIR로 컴파일합니다. 예전 interview namespace 대신 현재 canonical authoring 경계입니다.

work-discovery

예시 결과물로 업무 방법을 찾는 control plane입니다. 직접 업무를 계속 실행하는 엔진이 아니라, 마지막에 WorkflowIR을 만듭니다.

runtime

저장된 WorkflowIR의 step을 실제로 수행합니다. approval, execution log, scheduler, trigger 정책이 여기 있습니다.

현재 module package 목록

registerAllModules()가 bootstrap에서 명시적으로 등록하는 canonical package는 Gmail, Slack, local-folder, document, RDB, local-sheet, transform, HTTP, webhook입니다.

OpenAPI와 MCP도 현재 Core/desktop에 직접 연결되는 코드와 테스트가 남아 있지만 canonical ALL_MODULE_PACKAGES 목록과는 별도 경로입니다. 둘을 계속 지원할 계획이면 module package/catalog/trigger/discovery 경계로 통합할지 결정해야 합니다.

5. 실제 저장 위치

Windows 기준 기본 루트는 %LOCALAPPDATA%\AXStudio\입니다. 사용자의 업무 데이터는 기본적으로 이 PC에 남고, AI·Gmail·Slack 호출 때만 해당 외부 서비스로 나갑니다.

현재 디스크 구조

%LOCALAPPDATA%\AXStudio\
├─ data\
│  └─ ax-studio.db                  ← 핵심 SQLite
├─ artifacts\                       ← Work Discovery 원본/메타데이터
│  ├─ art_xxx_file.pdf              ← 복사된 원본
│  ├─ art_xxx.json                  ← sha256·경로·크기 메타데이터
│  ├─ art_xxx.document.json         ← PDF 정규화 문서 참조
│  └─ art_xxx.table.json             ← 생성된 표 artifact가 있을 때
├─ discovery\
│  └─ snapshots\                   ← source 읽기 결과 JSON manifest

7. 파일·문서·시트는 어떻게 읽히는가?

PDF / 문서

파일을 ArtifactStore에 복사하고 SHA-256으로 ID를 만듭니다. PDF면 Node Core가 Python worker에 JSON 요청을 보내 Document Engine이 문서 artifact를 만듭니다.

manifest.json · pages/*.txt · chunks.jsonl · images/ · tables/

CSV / XLSX / XLS

local-sheet가 workbook과 table을 만들고, 열 타입·행·profile을 정규화합니다. 기본 표 읽기 한도는 5,000행, workbook은 최대 20개 sheet입니다.

WorkbookArtifact → TableArtifact → OutputObservation

SQLite RDB

Work Discovery의 source provider는 현재 SQLite 파일을 read-only로 열어 허용된 table만 보고, 기본 rowLimit은 200입니다.

rdb:table → 제한된 snapshot → fingerprint

문서 처리의 실제 프로세스 경계

1
Node Core가 Python worker를 spawnstdin으로 { id, command, params } JSON을 보냅니다.
2
Python이 adapter를 선택engine: auto이면 Docling을 시도하고 실패 시 basic adapter로 fallback할 수 있습니다.
3
manifest를 commit marker로 저장payload를 먼저 쓴 뒤 manifest를 교체해 부분 결과를 완성 artifact로 보이지 않게 합니다.
4
Node가 JSON response를 받음페이지·청크·검색 결과를 Runtime과 Work Discovery가 사용할 수 있는 DocumentArtifact로 변환합니다.
현재 Work Discovery의 관찰 로직은 PDF/문서에서는 라벨 옆 숫자와 숫자+단위 패턴을 중심으로 찾고, 표에서는 숫자형 열의 값들을 관찰합니다. 모든 문서 의미를 자동으로 이해하는 단계는 아닙니다.

8. 발견한 업무가 실제로 실행되는 순간

Work Discovery가 끝났다고 바로 외부 메일을 보내는 것이 아닙니다. 발견 단계는 실행 설계도를 만드는 단계이고, 실제 실행은 기존 Runtime의 계약·승인·연결 검증을 다시 통과합니다.

Publish 시점

1
canPublish 확인status가 ready_to_publish이고 pending question이 없어야 합니다.
2
Blueprint 생성accepted candidate의 source·mapping·confidence·replay summary를 묶습니다.
3
WorkflowIR 컴파일source마다 local_sheet/rdb read step을 만들고, 필드마다 transform.evaluate step을 만듭니다.
4
workflow 저장workflow_versions.ir_json에 버전이 생기고 discovery session에 published workflow ID가 기록됩니다.

Runtime 실행 시점

1
사전 검증WorkflowIR schema, capability contract, 연결 상태, global/workflow active를 확인합니다.
2
execution 생성running 상태와 실행 당시 IR snapshot을 먼저 저장합니다.
3
step 실행·로그connector를 호출하고 log_json에 진행 상황을 누적합니다.
4
성공·실패·승인 대기외부 부작용은 approval policy를 거치고, pending이면 checkpoint를 저장해 재개합니다.

수동

workflow.run이 저장된 ID를 받아 Runtime을 호출합니다.

예약

Scheduler가 약 30초마다 schedule/once를 검사하고 마지막 실행 시각을 settings에 기록합니다.

이벤트

TriggerEngine이 polling/push/webhook을 받고 cursor와 trigger_receipts로 중복 실행을 줄입니다.

9. 일반 채팅은 어떻게 달라졌나?

기존 인터뷰 전용 흐름 대신 현재 workspace는 명령형 채팅에 가깝습니다. AI 답변은 텍스트만 보내는 것이 아니라, 검토 카드·입력 요청·workflow 변경 결과를 구조화해 host가 렌더링합니다.

1
ax:sendCommandChatRenderer가 최근 대화와 마지막 user message를 IPC로 보냅니다.
2
Command ChatAgentHarness가 AI를 호출하고 AxCommandService 명령을 처리합니다.
3
호스트 콜백command result, input request, presentation을 수집합니다. presentation action은 실행 명령이 아닙니다.
4
화면 응답assistant 메시지와 구조화된 UI를 Renderer에 반환합니다.
5
저장대화는 workspace_chats.messages_json에 저장되고 workflow ID와 연결할 수 있습니다.

11. 현재 코드에서 꼭 기억할 주의점

아래는 오류라고 단정한 목록이 아니라, 지금 구조를 완성품 수준으로 가져갈 때 우선 확인해야 할 지점입니다.

우선도현재 관찰왜 중요한가다음 검증/개선
P1 discovery.start 입력은 desiredRecurrence를 받지만, 현재 WorkDiscoveryService.start의 초기 state에 이 값을 넣지 않습니다. 사용자가 반복 주기를 줘도 blueprint의 schedule 제안까지 전달되지 않을 수 있습니다. state에 보존하고, “반복 주기 입력 → schedule trigger → Scheduler 실행” E2E 추가
P1 work_discovery_replay_cases 테이블은 migration에 존재하지만 현재 repository/service에서 쓰는 경로가 보이지 않습니다. 실제 replay 결과는 주로 session state_json 안에 있습니다. DB 설계와 실제 source of truth가 어긋나면 조회·보관·마이그레이션 정책이 혼란스러워집니다. 정규 replay case를 사용할지, 미사용 표를 제거할지 결정
P1 Work Discovery pipeline의 실행 집합은 메모리 Set이고 startup resume 경로가 없습니다. 앱 종료 중 탐색이 멈추면 session은 DB에 남지만 자동으로 이어지지 않습니다. 재시작 복구 상태, lease/timeout, 재실행 버튼 또는 안전한 resume 설계
P1 현재 UI의 useDiscovery는 기본적으로 예시 하나를 시작하고 inputArtifactIds: []로 호출합니다. Core schema/E2E는 여러 예시와 입력 artifact를 지원합니다. 제품 화면에서 가장 중요한 “여러 과거 사례로 재현 검증” 기능이 아직 command/E2E 경로와 동일하게 노출되지 않을 수 있습니다. UI에서 예시 최대 3개·입력 artifact 최대 10개를 선택하는 흐름 추가
P1 후보 enumerator는 숫자 관찰값과 제한된 변환식 중심입니다. 의미 기반 컬럼 매칭이나 임의 업무 로직을 모두 해결하지 않습니다. “무조건 알아서 배운다”는 제품 기대와 실제 deterministic 범위를 구분해야 합니다. 지원되는 업무 DSL 범위를 화면·문서·테스트에서 명확히 표시
P2 ArtifactStore는 파일 전체를 읽어 SHA-256을 계산하고, 기존 artifact를 찾을 때 JSON 파일들을 순회합니다. 큰 파일이나 artifact가 많아지면 import 지연과 I/O가 커질 수 있습니다. streaming hash, metadata index, artifact retention/backup 정책
P2 snapshot과 execution log는 계속 누적되며, Work Discovery snapshot의 보관·정리 정책이 명확하지 않습니다. 개인 PC의 디스크·DB 크기와 민감 데이터 잔존 기간이 늘어납니다. 보관 기간, 삭제, export/backup, 개인정보 정리 정책 정의
장점 계약 schema, catalog side effect, approval, command access, IPC sender 검증, sandbox/context isolation이 경계로 존재합니다. 기능이 늘어도 AI·UI가 바로 OS/connector 권한을 얻지 않도록 막는 기반입니다. 새 command/module 추가 때 동일한 contract·access·E2E 체크 유지

13. 기억할 것

무엇인가?

AX Studio는 로컬 PC에서 AI에게 업무를 맡기고, 결과를 workflow로 반복 실행하는 Electron 앱입니다.

새 핵심은?

결과물을 보여주면 연결된 자료를 제한적으로 조사하고, 과거 예시를 재현한 뒤에만 업무로 publish하는 Work Discovery입니다.

개발 질문은?

“이 입력이 어느 command를 타고, 어떤 artifact/DB JSON이 바뀌며, 재시작 후 같은 판단을 다시 복구할 수 있는가?”를 기능마다 답해야 합니다.

비유: 화면은 접수 창구, AxCommandService는 출입 통제, Work Discovery는 과거 작업을 조사하는 분석팀, WorkflowIR은 작업 지시서, Runtime은 실제 작업반, SQLite와 artifacts는 작업 대장과 자료 보관함입니다.

비유의 한계: 실제로는 한 PC 안의 여러 프로세스와 외부 네트워크가 섞여 있으므로, 장애·인증 만료·파일 변경·앱 재시작을 별도 상태로 다뤄야 합니다.
