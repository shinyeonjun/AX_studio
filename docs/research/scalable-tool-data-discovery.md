# AX: 대규모 도구·데이터 발견 구조 조사

조사일: 2026-09-05. 연구·설계 제안이며 구현 완료 명세가 아니다.
범위: 공식 자료, 코드 일부 확인. 제품 코드·draw.io·실데이터·동결 benchmark는 수정하지 않는다.

## 결론

Progressive disclosure 하나가 아니라, 권한을 반영한 카탈로그 → 후보 검색 → 필요한 계약·증거만 로딩 → 구조화된 계획 → 엔진 검증·실행의 조합이 필요하다. AI는 의미와 의도를 해석하고 다음 증거/작업을 제안한다. 검색, 접근 제어, 조회, 계산, 파일 생성, 재시도는 AX가 구현한 기능으로 수행한다. 임의 생성 코드를 실행하는 에이전트 샌드박스를 도입하자는 제안이 아니다.

## 공식 근거와 적용 범위

1. Anthropic Tool Search는 전체 도구 설명을 선행 로딩하지 않고 검색 결과의 정의만 펼친다. regex/BM25/custom 검색을 설명하며, 검색 단계가 지연을 추가하는 trade-off도 명시한다. 제공자의 자체 실험 수치를 AX의 개선율로 사용하면 안 된다. 해당 글의 programmatic calling은 모델 생성 코드 실행까지 포함하므로 AX에는 그대로 채택하지 않는다. [Advanced tool use](https://www.anthropic.com/engineering/advanced-tool-use)
2. Just-in-time context는 경로·식별자 등 가벼운 참조를 보관하고 필요한 내용을 도구로 읽는다. 사전 검색과 실행 중 추가 탐색을 혼합할 수 있지만 탐색의 비용·막다른 경로도 존재한다. [Context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)
3. Azure AI Search는 전문 검색과 벡터 검색 결과를 합치는 hybrid retrieval을 설명한다. 이름·ID의 정확 일치와 표현의 의미적 유사성은 상호 보완적이다. AX에 Azure 서비스 자체가 필요하다는 뜻은 아니다. [Hybrid search](https://learn.microsoft.com/en-us/azure/search/hybrid-search-overview)
4. MCP 2025-06-18 문서의 tools/list는 페이지네이션과 목록 변경 알림을 지원한다. 이는 도구 목록 동기화 계약이지 업무 의미 검색기의 완제품이 아니다. 신뢰하지 않는 서버의 도구 annotation을 보안 정책의 근거로 삼으면 안 된다. 버전을 특정해 참고한 것이며 최신 버전이라고 단정하지 않는다. [MCP tools](https://modelcontextprotocol.io/specification/2025-06-18/server/tools)

## 세 개의 서로 다른 검색 대상

구조화 데이터의 추가 근거: Snowflake는 비즈니스 정의를 semantic view로 보완하며, dbt MetricFlow는 entity 관계로 조인과 fan-out을 제약한다. 검색한 테이블의 관련성과 올바른 집계 단위는 다른 문제다. [Snowflake](https://docs.snowflake.com/en/user-guide/snowflake-cortex/cortex-analyst), [dbt join logic](https://docs.getdbt.com/docs/build/join-logic).

기업형 workflow 평가인 Spider 2.0은 많은 컬럼과 메타데이터·문서 탐색을 포함한다. 단순한 질문→SQL 한 번으로 실제 업무 난도를 대표하기 어렵다는 근거이며 AX 성능을 측정한 자료는 아니다. [논문](https://arxiv.org/abs/2411.07763). 상세 조사와 버전별 주의점은 [데이터 Discovery 근거](data-discovery-evidence.md)에 기록했다.

| 대상 | 카탈로그에 필요한 정보 | 상세 내용 로딩 |
| --- | --- | --- |
| 기능/도구 | ID, 역할, 입력·출력, side effect, 연결 요구, 버전, 실행 가능 여부 | 선택한 capability 계약만 |
| 원천 데이터 | 소유 연결, 객체 ID, 스키마, 열 설명, 기간 범위, 단위, grain, 관계, 갱신 시점, 권한 | 스키마·프로파일 → 제한된 증거 → 필요한 실제 조회 |
| 문서/예시 | 파일 ID, 역할, 페이지·섹션, 출처, 추출 상태, 버전 | 관련 항목·표·페이지 이미지 |

권한은 검색 후 실행 시점만이 아니라 검색 후보·스니펫에도 반영한다. 실제 권한은 실행 직전에 재검사한다. 카탈로그가 권한 판단의 유일한 근거가 되어서는 안 된다.

## AX용 제안 흐름

1. **의도 구조화:** AI가 목적, 대상 기간, 원하는 결과물, 금지 동작, 필요한 정보 유형을 제안한다. 고정 업무명 매핑으로 분기하지 않는다.
2. **후보 검색:** 엔진이 권한·자료형 등 확실한 조건을 적용하고 키워드/정확 이름 검색을 수행한다. 동의어·언어 간 검색 실패가 측정되면 의미 검색을 결합한다. 고정 top-k를 진실의 경계로 쓰지 않는다.
3. **증거 확대:** 선택한 객체의 설명·스키마·프로파일·관련 문서·실제 선언된 관계를 읽는다. 추가 후보가 필요하면 검색 폭을 넓힌다. 컬럼명이 비슷하다는 이유로 join을 확정하지 않는다.
4. **계획 제안:** AI가 필요한 source/field/filter/join/aggregate/output binding을 구조화해 제안한다. 각 선택에 확인한 source ID와 근거를 연결한다.
5. **엔진 검증:** 지원 연산, 타입, 권한, 기간, 단위, join cardinality, 데이터 완전성, 예시 replay, 출력 용량을 확인한다. 지원하지 않는 연산은 거절하거나 질문한다.
6. **엔진 실행:** 승인된 연산만 source-side query 또는 제한된 로컬 실행기로 처리한다. 대용량 결과는 파일/결과 참조로 유지하고 모델에는 필요한 증거만 전달한다.
7. **복구와 결과:** 단계별 상태와 evidence 버전을 저장한다. 실패 시 전체 추론을 무조건 반복하지 않는다. 출력 검증 후 사용자에게 결과를 제공한다.

업무별 실행은 동적으로 달라질 수 있다. 위 순서는 모든 업무를 고정 7단계 템플릿으로 하드코딩하자는 의미가 아니다. 반복 탐색의 연산·시간·비용 예산은 엔진이 통제한다.

## 대량 데이터를 다루는 핵심

- 백만 행을 AI 입력으로 보내는 것과 백만 행을 정확히 처리하는 것은 다르다. 필요한 전체 범위는 엔진이 조회·집계한다.
- 필터·projection·집계 pushdown, 페이지 처리, 스트리밍 또는 로컬 spill은 엔진 기능이다. 지원 범위를 넘으면 부분 결과를 완전한 결과로 보고하지 않는다.
- 샘플은 의미 추론의 증거이며 SUM/COUNT 결과의 대체물이 아니다. 희귀 상태, 중복, null은 샘플에 없을 수 있다.
- 카탈로그는 전체 레코드의 벡터화보다 객체·스키마·설명·문서 구간을 중심으로 시작한다. 변경 버전과 삭제/권한 회수에 맞춰 무효화한다.
- 테이블 의미, grain, 통화, 시간대, 기준 시각은 사용자/DB/문서의 검증된 메타데이터로 관리한다. AI가 추론한 설명은 검증된 정의와 구별한다. 테스트 정답에서 가져온 업무별 규칙을 카탈로그에 심지 않는다.
- 원천 내용을 신뢰할 수 있는 실행 지시로 승격하지 않는다. 도구 설명과 문서도 prompt injection 입력이 될 수 있다.

## 이번 timeout과의 관계

직전 로컬 로그 관찰: 조회 계획 58,250자·이미지6장/43.289초 완료, 계산 규칙 추론 60,111자·이미지6장/180초 timeout. 문자 수는 토큰 수가 아니다. 이 수치만으로 연결 개수, 입력 크기, 모델 서비스 지연 중 원인을 확정할 수 없다.

확인한 현재 코드:
- `catalog/dynamic-catalog.ts`: ID별 동적 capability 등록/목록.
- `catalog/capability-resolver.ts`: 등록된 capability의 ID/alias 해석.
- `report-generation/planner/planner.ts`: 계산 추론에 exampleSources·PDF geometry·이미지를 전달.

위 일부 경로 확인만으로 전체 제품에 검색 기능이 전혀 없다고 결론 내리지는 않는다. 기존 카탈로그/검증/계산기를 유지하며 검색과 증거 전달 경계를 보완하는 것이 제안의 출발점이다.

## 안전한 도입과 검증

1. 먼저 관측: 호출별 입력 구성 크기, 실제 모델, 첫 응답/종료 시각, 출력량, 검색 후보, 선택 근거, 데이터 처리 건수, 실패 단계를 수집한다. 원문·비밀정보는 기본 로그에서 제외한다.
2. 기존 catalog에 조회 가능한 요약과 선택적 상세 로딩을 붙인다. 후보 recall을 측정한 뒤 검색 방식을 확장한다.
3. 데이터·문서 증거의 참조/범위 조회와 계획의 source grounding을 추가한다.
4. 대용량 쿼리와 로컬 실행 용량을 단계적으로 확장하고, 반복 탐색·checkpoint·예산 처리를 통합한다.

별도 평가 세트 제안(기존 동결 v1 불변): 도구 10/100/1000, 테이블 수와 데이터 행 수를 독립적으로 변화시킨다. 같은 이름의 도구, backup source, 다국어 표현, 관계를 통해서만 찾을 수 있는 source, 정답 없음, schema drift, 권한 회수, 희귀 예외, 악성 설명을 포함한다.

측정 계약:
- 후보 recall@k: 필요한 gold source/tool 중 후보에 포함된 수 / 필요한 gold 수. 필수 집합이 전부 포함된 task 비율도 별도 기록.
- 실행 가능 계획 비율: 실제 계약 검증 통과 계획 / 제안 계획. 의미적 정답률과 구분.
- 결과 정확도: 독립 정답 일치 task / 정답 평가 가능 task. 보류를 성공으로 계산하지 않음.
- 위험 실행: 승인·권한 위반 실행 수 / 시도 수, 잘못 확정한 결과 수 / 확정 결과 수. 분자·분모 함께 보고.
- p50/p95 총 지연, 호출별 지연, timeout 수/전체 실행 수, clarification, 모델 입출력량, 원천 처리량.

비교: 전체 선행 로딩 / 선택 로딩 / 선택 로딩+증거 확대. 같은 사례·모델·권한·정답 계약을 유지한다. 입력이 줄었다는 사실만으로 정확성과 속도가 개선됐다고 주장하지 않는다.

## 2026-09-05 보충: 보고서 원천 재계획 이후 재조사

앞 부분은 이전 조사 기록이다. 아래는 `report_source_replan_no_progress` 화면 제시 이후 현재 코드를 다시 읽고 수행한 조사다. 이 보충은 설계 제안이며 제품 패치나 해당 실행의 근본 원인 확정이 아니다. 실제 실행 ID의 checkpoint는 이번 조사에서 열지 않았다.

### 확인한 현재 구현의 경계

- `modules/rdb/connector.ts`의 `schema.describe`는 테이블 이름 배열을 반환한다. 보고서의 최초 원천 선택 시점에는 이 호출을 통해 컬럼 타입·설명·키·관계를 얻지 않는다.
- `report-generation/planner/planner.ts`의 `inferCapturePlan` 입력은 PDF 근거, HTTP 연결 요약, DB 테이블 이름, 필수 원천 및 이전 계획이다. 이 호출 안에서 후보별 스키마 탐색 도구를 반복 호출하는 구조는 아니다.
- `planner/schema.ts`의 coverage 검사는 요구 ID와 선택 alias의 존재 및 http/rdb 종류를 확인한다. 금액의 업무 정의, 행 단위, 통화, 기간, 조인 의미까지 입증하는 검사는 아니다. AI가 생성한 requirements 역시 오류 가능한 가설이다.
- `planner/evidence.ts`는 이미 조회한 snapshot의 제한된 행·프로파일·PDF 페이지를 제공한다. 원천 누락은 typed sourceRequest로 계획 단계에 돌려보낸다.
- `service.ts`의 재계획은 이전 원천 유지와 추가만 허용한다. 최초 선택 오류의 교체를 막을 수 있다는 설계상 제약이 있다. 동일 capturePlan 또는 동일 계획+bindings의 반복으로 no-progress를 판단한다. 새로운 증거를 얻었는지와 계획 문자열이 달라졌는지는 다른 개념이다.
- 제품 전체에 검색/OpenAPI가 없다는 뜻은 아니다. `openapi/ingest.ts`는 OpenAPI를 dynamic capability로 등록하고, `retrieval/search.ts`는 로컬 파일 검색을 제공한다. 이 자산을 보고서 원천 발견 경로와 연결하는 것이 신규 병렬 인프라보다 우선이다.

서로 다른 논문의 데이터셋·모델·비용·평가지표를 섞어 우열이나 AX 예상 성공률을 계산하지 않는다. 이 자료들은 설계 근거이지 이번 실패의 원인 증명이나 완전 자동화 보증이 아니다.

### 권장 구조: 계획 반복이 아니라 근거를 확보하는 반복

1. 사용자 제약(금지 동작, 결과 형식, 기간)과 AI가 추론한 데이터 필요조건을 분리한다. 전자는 임의로 바꾸지 않는다. 후자는 새로운 근거에 따라 버전과 이유를 남기고 수정 가능해야 한다.
2. 호스트가 권한 범위 내 원천 카탈로그를 검색한다. 도구·원천·문서 인덱스는 역할을 구별한다. 연결 ID 하나를 데이터셋 하나로 취급하지 않는다.
3. AI는 후보를 보고 스키마/설명/관계/기간/제한된 프로파일 중 무엇이 필요한지 요청한다. 호스트는 제공된 ID와 선언된 연산을 검증한 후 증거를 반환한다.
4. 충분한 근거가 모이면 source/field/join/filter/aggregate/output binding을 포함한 기존 선언형 계획으로 연결한다. 지원되지 않는 연산은 명확히 분리한다.
5. 호스트가 예시 기간 데이터로 계산·재현 검증한다. 통과한 뒤에만 대상 기간 계산과 PDF 생성을 진행한다.
6. 불충분하면 실패를 분류한다: 후보 미발견, 스키마 미확인, 권한 없음, 기간 데이터 없음, 단위/관계 불일치, 의미 모호, 연산 미지원. 분류별로 검색 확대·상세 조회·계획 수정·사용자 질문·중단 중 하나를 선택한다.

진전 없음의 제안 키는 정규화된 행동+대상+인자+증거 버전이다. 동일 행동으로 새 정보가 없으면 반복하지 않는다. 반대로 계획이 같더라도 새 메타데이터로 검증이 진전되는 상황은 허용해야 한다. 모델이 말하는 자신감 증가만을 진전으로 인정하지 않는다. 총 시간·호출·행/바이트·동시성 예산은 유지한다.

원천 교체는 기존 snapshot을 수정하는 방식이 아니라 새 계획 버전으로 제안한다. 권한·사용자 제약을 다시 검사하고 영향받은 계산·replay 결과만 무효화해 재검증한다. 기존 실행 증거는 보존한다. 기존 ADR의 근거 보존 원칙과 양립시켜야 한다.

업무별 정답 수식이나 source 매핑을 코드/카탈로그에 몰래 넣지 않는다. DB 선언·API 명세·실제 업무 문서·사용자 확인에서 온 의미 정보와 AI 가설은 출처·검증 상태를 구별한다. 일반 메타데이터 모델은 하드코딩이 아니지만, benchmark gold를 주입하면 평가 누출이다.

### 다음 작업 순서와 살충제 패러독스 방지

1. 최신 실패 실행의 requirements, 후보, 선택, 추가 근거 요청, 계획 diff를 읽고 사례를 분류한다. 새 논문을 발견했다는 이유로 즉시 현재 실패 원인을 확정하지 않는다.
2. DB 상세 메타데이터와 OpenAPI operation을 보고서 원천 선택 전에 조회하는 경로를 먼저 만든다. 현재 pipeline을 교체하기보다 실제 연결을 복구한다.
3. evidence 기반 검색·검증 루프와 구체적 clarification을 구현한다. 잘못된 AI 가설을 수정할 수 있게 하되 사용자 제약과 기존 snapshot은 보존한다.
4. 카탈로그가 커졌을 때 후보 recall·지연을 보고 BM25/의미 검색을 선택한다. 대량 실행기의 확장은 별도 측정으로 판단한다.

기존 동결 benchmark는 유지하고 새로운 평가 묶음으로 비교한다. 도구/테이블 수와 행 수를 독립적으로 변화시킨다. 숫자·ID·순서 변형만으로는 부족하다: 새 업무 유형, 다른 source 조합, 잘못된 최초 가설의 교체, 동일 계획+새 증거, 같은 이름의 backup, 누락된 관계, 과거 이력 부재, 단위·통화 차이, 합법적인 0건, 정답 없음, 권한 회수, 악성 설명을 포함한다. hidden holdout은 탐색·수정 판단에 노출하지 않는다.

측정은 필수 원천 집합 전체 recall, 결과 정확도, 잘못 확정한 결과/확정한 전체 결과, 정답 가능 업무의 불필요 중단/정답 가능 업무 수, 원인별 복구율, 질문 수, p50/p95 지연과 호출비용이다. 같은 입력·증거 버전의 모델 반복과 서로 다른 구조의 업무 일반화도 구별한다. 이 보충 조사에서는 새로운 benchmark나 성능 실험을 실행하지 않았다.

## 2026-09-05 보충: 개발자 커뮤니티의 원문 사례

아래는 프로젝트 운영 저장소의 원문 이슈·토론 4건을 직접 읽고 요약한 것이다. 작성자의 경험·제안과 제한된 비교 실험을 구분하며, 발생 빈도나 AX의 원인을 추정하는 표본으로 사용하지 않는다. 운영 저장소에 등록됐다는 사실이 유지관리자의 원인 확인을 의미하지는 않는다.

- **도구 검색 누락 — 개인 재현 보고.** opcode81은 Claude Code 2.1.169에서 Serena의 `find_symbol`이 `find symbol` 검색에 나타나지 않고, 모델이 스스로 요청하는 5개 결과 밖의 도구를 찾지 못했다고 보고했다(2026-06-09). 이름보다 긴 설명이 순위에 유리하다는 설명은 작성자의 가설이며 순위 알고리즘 검증 결과가 아니다. 도구가 존재한다는 인식과 검색 후보에 포함되는 것은 다를 수 있다는 구체적 사례다. [Claude Code #66488](https://github.com/anthropics/claude-code/issues/66488)
- **도구 스키마와 실행 전제 — 개발자 문제 제기·설계 토론.** ZachGerman은 필요한 서버·클라이언트 capability가 없는데도 호출되는 문제를 출발점으로 `requires` 필드를 제안했다(2025-08-15). 권한·선행 호출 상태까지 표현하자는 제안에 jonathanhefner는 client capability 또는 결과의 `next` 힌트로 표현할 가능성을 질문했다. 도구 발견과 실행 전제 표현 사이의 간극을 논의한 원문이며, 제안의 표준 채택이나 성능 개선이 입증된 자료는 아니다. [MCP Discussion #1351](https://github.com/modelcontextprotocol/modelcontextprotocol/discussions/1351)
- **열 이름과 업무 의미 — 사용자 경험에 근거한 기능 요청.** Gamsheiev는 DBeaver 25.1.0·Oracle 환경에서 `AR_CFAMIN` 같은 불명확한 이름 때문에 열 주석을 툴팁보다 잘 보이게 표시해 달라고 요청했다(2025-06-11). 열 목록을 확인해도 설명을 별도로 찾아야 하는 사람의 작업 사례다. AI의 schema discovery 정확도나 주석 제공 효과를 측정한 실험은 아니다. [DBeaver #38363](https://github.com/dbeaver/dbeaver/issues/38363)
- **성공 결과 뒤 동일 호출 반복 — 재현 코드와 제한된 비교가 있는 보고.** gucasbrg는 DashScope의 Kimi K2.5가 `read`→`exec` 성공 결과 뒤 같은 호출을 다시 생성한다고 보고하고, 동일 메시지열에서 다른 6개 모델은 텍스트로 종료했다는 표와 재현 코드를 공개했다(2026-03-04). 앞에 인사 대화를 추가하면 반복이 사라졌다는 관찰도 있다. 단순 일화보다 비교 조건이 구체적이지만 독립 재현·반복 시행 통계가 없는 작성자 실험이다. 첨부 자동 검사도 동일 인수 비교가 아니라 연속 `tool_calls` 여부를 판정하므로, 그 검사만으로 모든 반복이 무진행이라고 확정할 수 없다. 이번 조사에서는 코드를 실행하지 않았다. [Kimi-K2.5 #24](https://github.com/MoonshotAI/Kimi-K2.5/issues/24)

AX와의 관련성은 증상 구분에 한정한다. 사용자 제공 최신 오류인 ‘같은 계획 반복·진행 없음’은 위 반복 호출 사례와 유사한 관찰 대상이지만, 검색 누락·의미 정보 부족·결과 반영 실패 중 무엇이 원인인지는 이 자료로 판정할 수 없다. 결정론적 호스트 도구가 실행하고 AI는 의미 기반 계획만 제안한다는 AX 경계를 유지하며, 외부 사례의 `exec`를 임의 코드 실행 도입 근거로 해석하지 않는다. 이 보충은 주 아키텍처 권고나 기존 timeout 진단을 변경하지 않는다.
