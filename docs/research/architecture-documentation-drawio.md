# AX Studio 아키텍처 시각화 조사

조사일: 2026-09-05. 저장소 기준 커밋: `3529587`.
범위: 공식 문서와 공개 프로젝트 사례를 통한 문서화 수준 조사. 제품 코드와 기존 설계 결정은 수정하지 않았고, 다이어그램은 아직 작성하지 않았다.

## 결론

`.drawio/`에서 편집 가능한 아키텍처 그림을 관리하는 방향은 적절하다. 폴더는 존재하며 조사 시점에는 비어 있다. 모든 함수와 클래스를 수작업으로 그리기보다, 전체 경계와 핵심 업무의 실행·데이터·실패 흐름을 나누어 기록한다. 아래 권고는 공식 방법론과 사례에서 도출한 AX Studio용 제안이며 업계 전체의 관행을 통계적으로 조사한 결과는 아니다.

## 공식 가이드와 실제 사례

- **C4**는 시스템 맥락, 컨테이너, 컴포넌트, 코드의 확대 수준을 구분한다. 모든 수준이 필수는 아니며 대부분의 팀에는 맥락과 컨테이너 그림으로 충분하다고 설명한다. [C4 diagrams](https://c4model.com/diagrams)
- 컴포넌트 상세는 가치가 있을 때 선택하며, 장기간 유지할 코드 수준 그림은 자동 생성을 고려한다. 모든 메서드를 나열하는 문서를 권장하지 않는다. [Component diagram](https://c4model.com/diagrams/component), [Code diagram](https://c4model.com/diagrams/code)
- **arc42**는 주요 기능, 외부 연동, 시작·종료, 오류·예외를 실행 관점의 문서 대상으로 삼는다. 전체 시나리오의 개수보다 아키텍처적으로 중요한 대표 사례가 중요하다. 시퀀스, 활동 흐름, 상태 머신 등을 사용할 수 있다. [Runtime view](https://docs.arc42.org/section-6/)
- **Backstage** 공개 문서는 전체 구조뿐 아니라 구성요소 간 통신, 배포 단위, 데이터베이스 격리와 의존성 규칙을 설명한다. 그림에 책임·제약을 연결하는 실제 사례다. [Architecture overview](https://backstage.io/docs/overview/architecture-overview/)
- **AWS ADR 가이드**는 맥락·결정·결과를 남기고 결정 이력을 보존하도록 설명한다. 그림이 구조를 보여준다면 ADR은 선택의 이유와 영향을 기록한다. [ADR process](https://docs.aws.amazon.com/prescriptive-guidance/latest/architectural-decision-records/adr-process.html)
- **draw.io**는 C4 도형 라이브러리와 UML 도형을 제공한다. 현재 선택한 도구로 시작할 수 있다. [C4 modelling](https://www.drawio.com/docs/diagram-types/c4-modelling/)

## AX Studio에 제안하는 문서 범위

다음은 작성 계획이지 검증을 마친 현재 아키텍처 명세가 아니다. 실제 작성 단계에서는 현재 코드와 테스트로 각 연결·상태를 확인해야 한다.

| 문서 | 설명해야 하는 질문 | 상세 수준 |
| --- | --- | --- |
| 01 시스템 맥락 | 사용자, AX, 모델 제공자, API·DB·외부 서비스는 어떻게 연결되는가? | 내부 모듈 없이 시스템 경계 중심 |
| 02 실행 구조와 배포 | Electron 화면·메인, Python 엔진, CLI, 로컬 저장소는 어디서 실행되고 통신하는가? | 프로세스·저장소·프로토콜 중심. Core 패키지를 별도 서버처럼 그리지 않음 |
| 03 보고서 생성 시퀀스 | 채팅 요청부터 자료 분석, 조회, 계산 검증, PDF 생성, 결과 전달까지 누가 무엇을 하는가? | 주요 호출, 비동기 경계, 오류 반환 지점 |
| 04 상태와 복구 | 접수·실행·실패·완료는 무엇으로 바뀌고 어느 지점부터 재시도 가능한가? | 상태 전이 조건과 상태 소유자. 단일 실행과 Work Discovery를 별도 페이지로 구분 |
| 05 데이터 흐름과 보관 | 예시·템플릿·원본 조회·스냅샷·계산 결과·PDF가 어떻게 이동하고 저장되는가? | 읽기/쓰기, 세션 소유권, 저장 위치, 외부로 나가는 데이터 |
| 06 반복 업무 발견과 승인 | 예시 검증, 모호성 질문, 사용자 확정, 반복 실행·외부 동작 승인은 어떻게 다른가? | 업무 발견/게시/실행의 경계와 승인 대상 |

첫 작성은 01·02로 공통 지도를 잡고, 반복 오류를 이해하는 데 필요한 03·04를 우선한다. 이후 05·06을 보완한다. 모듈 상세도·ERD·위협 모델은 실제 설명이 부족한 부분에 한해 추가한다. 이 여섯 문서는 업계 필수 장수가 아닌 프로젝트용 범위 제안이다.

## 그림의 품질 기준

공식 C4 권고는 제목·범위·범례, 구성요소의 역할·기술, 방향이 명확한 관계와 관계 이름·프로토콜을 요구한다. 색상만으로 의미를 전달하지 않는다. [Notation](https://c4model.com/diagrams/notation)

AX용 추가 운영 제안:

1. `현재 구현`과 `개선 제안`을 별도 파일 또는 페이지로 분리한다. 원하는 동작을 구현된 동작처럼 그리지 않는다.
2. 각 그림에 확인한 커밋, 날짜, 관련 코드·테스트·ADR 링크를 둔다. 확인하지 못한 연결은 `미확인`으로 표시한다.
3. 연결선에는 IPC, subprocess, HTTP GET, SQL read 등 실제 통신·동작을 표기한다. 논리적 의존성과 런타임 호출을 같은 선으로 혼합하지 않는다.
4. 오류 흐름에는 실패를 감지하는 곳, 사용자에게 전달하는 곳, 저장된 증거, 재시도 범위를 표시한다. 구현에 없는 자동 복구를 추가하지 않는다.
5. 이미지에 실제 비밀번호·토큰·개인 데이터는 넣지 않는다. 비밀정보 저장소와 접근 경계만 표시한다.
6. 함수명 수정마다 전체 그림을 고치지 않는다. 책임·호출 경계·상태 전이·저장 방식·권한이 변하는 변경에서 관련 그림을 함께 검토한다.
7. `.drawio` 원본을 Git으로 관리하고 필요하면 SVG/PDF 미리보기를 함께 제공한다. 변경 이유는 기존 `docs/adr/`에 기록하고 그림에서 연결한다.

## 충분히 작성했는지 판단하는 질문

- 처음 보는 사람이 요청의 시작점과 최종 결과 저장 위치를 찾을 수 있는가?
- 오류가 발생했을 때 어느 구성요소의 로그·테스트를 확인할지 알 수 있는가?
- 데이터 조회, 모델 판단, 결정적 계산, PDF 렌더링의 책임이 구분되는가?
- 단일 작업 완료, 업무 게시, 외부 전송 승인을 혼동하지 않는가?
- 구현 사실과 설계 의도 사이의 차이를 확인할 수 있는가?

이 질문에 답할 수 있으면 유용한 기준 문서다. 코드 전체를 그림으로 복제할 필요는 없다.
