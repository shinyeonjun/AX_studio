백엔드가 어디서 어떻게 움직이고, 무엇을 저장하는가

현재 코드를 기준으로, “화면에서 버튼을 눌렀을 때 어디로 가는지”와 “그 결과가 어떤 파일·테이블·JSON으로 남는지”를 한 장으로 정리했습니다.

Windows 기준 로컬 Electron 앱 2026-08-23 코드 기준 외부 라이브러리 없음
한 문장 요약: AX Studio는 기본적으로 “인터넷의 별도 백엔드 서버”에 붙는 서비스가 아니라, 화면(Renderer) → 안전한 통로(Preload/IPC) → 권한 있는 프로세스(Main/Core) → 로컬 SQLite·파일·외부 연결 순서로 움직이는 데스크톱 앱입니다.

1. 전체 그림: 이 앱의 “백엔드”는 어디인가?

이 프로젝트에서 백엔드라고 부를 만한 부분은 별도 Node 서버 하나가 아니라, Electron의 Main 프로세스와 그 안에서 실행되는 Core입니다. 화면은 직접 파일이나 비밀키를 만지지 않고 IPC를 통해 요청합니다.

프로그램 내부 흐름 로컬 디스크 네트워크 비밀 데이터
1

화면이 요청한다

React가 “워크플로 저장”, “채팅 보내기”, “실행” 같은 명령을 만듭니다.

window.ax.saveWorkflow(...)
2

IPC가 운반한다

Preload가 허용한 채널로만 Main 프로세스에 전달합니다.

ipcRenderer.invoke('ax:...')
3

Core가 판단한다

JSON 형식, 권한, 연결 상태, 승인 여부를 확인합니다.

parse → validate → execute
4

Runtime이 움직인다

스텝을 순서대로 실행하고 AI나 Gmail 같은 Connector를 호출합니다.

WorkflowRuntime
5

결과가 남는다

실행 기록은 DB에, 문서 산출물은 파일에, 비밀키는 암호화 파일에 남습니다.

SQLite + files + secrets

2. 실제로 무슨 일이 일어나는가?

A. 채팅 한 번 보내기

1
입력사용자가 채팅창에 문장을 입력합니다.
2
IPC 호출ax:sendChat 또는 workspace chat 명령이 Main으로 갑니다.
3
AI/상태 처리Core의 interview 또는 workspace 흐름이 AI를 호출하고 상태를 갱신합니다.
4
응답답변이 IPC를 거꾸로 타고 화면에 표시됩니다.
5
저장인터뷰 상태는 chat_sessions.state_json, workspace 메시지는 workspace_chats.messages_json에 들어갑니다.
채팅은 단순히 “문자열 한 줄”만 저장하는 게 아닙니다. 인터뷰는 다음 질문, draft, workflow 연결 상태까지 포함한 상태 객체를 JSON으로 저장합니다.

B. 워크플로 하나 실행하기

1
실행 시작수동 버튼, 스케줄, Gmail/Slack/폴더/webhook 이벤트가 시작점입니다.
2
사전 검사WorkflowIR 스키마, 연결, 전역 활성화, 워크플로 활성화, 계약을 확인합니다.
3
실행 행 생성executions에 running 상태와 실행 당시 IR 복사본을 먼저 남깁니다.
4
스텝 수행각 action/if/AI/approval 스텝을 실행하고 로그 배열을 계속 업데이트합니다.
5
끝 또는 대기success/failed/cancelled가 되거나, 사람 승인이 필요하면 pending_approval로 멈췄다가 재개합니다.
승인 대기는 실패가 아닙니다. 실행 당시 변수와 남은 스텝을 checkpoint로 저장해 두었다가 승인 후 이어서 실행하는 구조입니다.

예약 실행

Scheduler가 약 30초마다 깨어나 활성 워크플로의 schedule/once를 확인합니다.

마지막 실행 시각: settings["scheduler.lastFired"]

이벤트 실행

TriggerEngine이 약 30초마다 polling하고, Slack 같은 push나 webhook 이벤트도 받습니다.

중복 방지: trigger_receipts + 메모리 집합

문서 처리

Core가 별도 Python worker를 실행해 문서를 읽고, 결과를 manifest/pages/chunks 파일로 저장합니다.

Node Core ↔ stdin/stdout JSON ↔ Python

3. 데이터는 어디에 저장되는가?

Windows에서 기본 루트는 %LOCALAPPDATA%\AXStudio\입니다. 실제로는 보통 C:\Users\사용자\AppData\Local\AXStudio\처럼 보입니다.

디스크 구조

%LOCALAPPDATA%\AXStudio\
├─ data\
│  └─ ax-studio.db             ← 핵심 SQLite 데이터베이스
├─ credentials\                 ← OS로 암호화한 토큰·refresh token
├─ config\
│  ├─ ai.toml                  ← AI 설정 일부
│  └─ migration.json           ← 저장소 레이아웃 마이그레이션 기록
├─ documents\                  ← 원본/문서 관련 데이터
├─ templates\
├─ generated\
│  ├─ reports\
│  └─ exports\
├─ cache\
│  ├─ chromium\
│  └─ document-engine\
└─ logs\

저장소별 역할

장소무엇이 들어가나
SQLite워크플로, 버전, 실행, 승인, 설정, 연결 메타데이터, 채팅, trigger receipt
credentialsSlack/Gmail/HTTP 등 토큰과 OAuth refresh token. Electron safeStorage로 암호화
documents/cache문서 페이지 텍스트, chunks JSONL, manifest, 이미지·표 같은 산출물
logs시작 실패나 운영 문제를 조사할 때 참고하는 로그
generated리포트·내보내기 결과가 생기는 자리
중요: ax-studio.db는 “엑셀 파일”처럼 보면서 고치는 파일이 아니라 SQLite 파일입니다. 직접 편집하기보다 앱의 repository/API를 통해 바꾸고, 백업 복사본을 먼저 만드는 편이 안전합니다.

4. SQLite 안에는 어떤 표가 있는가?

현재 코드의 핵심 스키마입니다. 테이블 안의 JSON 칸은 “JSON을 별도 파일로 저장한다”가 아니라, SQLite의 TEXT 칸에 JSON 문자열을 넣는 방식입니다.

테이블쉽게 말하면주요 칼럼
workflows워크플로의 현재 목록/스위치id, name, active, created/updated
workflow_versions워크플로의 실제 설계도와 버전 역사workflow_id, version, ir_json
executions실제로 돌린 한 번 한 번의 기록status, workflow/version, log_json, ir_json, trigger
approvals사람이 승인/거절해야 하는 지점execution_id, action_ids_json, status, payload_json
settings앱의 작은 전역 설정 저장소key, value_json
connections연결 상태와 비밀이 아닌 설정connector, connected, config_json
chat_sessions인터뷰형 대화의 재개 가능한 상태workflow_id, title, summary, state_json
workspace_chats일반 workspace 대화의 메시지 배열messages_json, title, created/updated
trigger_receipts같은 외부 이벤트를 다시 실행하지 않았는지 기록dedupe_key, status, execution_id, created/updated

5. 데이터 형식과 안전 경계

설계상 좋은 경계

JSON은 검증 후 실행

워크플로는 Zod 스키마로 읽고, 최대 스텝 수와 payload 크기도 검사합니다. 저장할 때도 persistence 계약을 확인합니다.

비밀 분리

DB에는 보통 메타데이터

연결 이름·종류·활성 여부 같은 정보는 DB에 두고, 토큰·refresh token은 OS 암호화 credentials 파일에 둡니다.

복구 설계

승인 지점은 재개 가능

승인 전 checkpoint에 변수, 결과, 남은 스텝을 담아 앱을 다시 켠 뒤에도 이어갈 수 있게 되어 있습니다.

Boolean·시간·ID의 실제 모양

BooleanSQLite에서는 보통 0/1, TypeScript로 읽을 때 false/true
시간ISO 문자열 예: 2026-08-23T10:20:04.000Z
ID대부분 randomUUID()로 만든 문자열
큰 객체JSON.stringify한 문자열. 읽을 때 JSON.parse하고 스키마를 재확인
실행 상태running, pending_approval, success, failed, cancelled

DB 엔진은 두 가지 경로

Core는 실행 환경에서 better-sqlite3 네이티브 어댑터를 먼저 시도하고, 사용할 수 없으면 sql.js로 fallback합니다. 두 경로 모두 SQLite 데이터를 다룹니다.

sql.js fallback에서는 DB 전체를 메모리에 읽고, 변경 후 DB 전체를 export해 파일에 씁니다. 현재 이 작업 환경에서는 better-sqlite3 네이티브 바인딩을 찾지 못해 테스트가 이 fallback 경로로 실행되었습니다. 실제 배포 환경에서는 두 경로를 모두 확인해야 합니다.

6. 비유로 다시 보기

비유: AX Studio는 작은 자동화 공장입니다

화면
고객 창구입니다. “이 일을 해주세요”라고 접수합니다.
IPC/Main
출입 통제와 접수처입니다. 아무 명령이나 공장 안으로 들이지 않습니다.
Runtime/Connector
작업반입니다. 메일, Slack, 파일, AI라는 외부 도구를 실제로 사용합니다.
SQLite
작업 대장입니다. 설계도, 작업 결과, 승인 기록을 적습니다.
credentials
열쇠 보관함입니다. 대장에 평문 열쇠를 적지 않습니다.
Scheduler/Trigger
알람과 우편함입니다. 시간이 되거나 새 이벤트가 오면 작업을 시작합니다.

비유가 멈추는 지점: 실제 공장과 달리 이것은 한 PC 안의 여러 프로세스와 외부 네트워크 호출이 섞인 프로그램입니다. 특히 AI·Gmail·Slack 호출은 네트워크 장애, 인증 만료, 속도 제한이 생길 수 있습니다.

7. 앱을 켜고 끌 때의 흐름

시작할 때

1
데이터 폴더 준비AXStudio 폴더와 하위 디렉터리를 만듭니다.
2
이전 저장소 마이그레이션예전 위치의 DB·credentials·문서·템플릿을 새 위치에 복사할 수 있습니다.
3
DB와 Core 생성SQLite, WorkflowStore, Runtime, AgentHarness를 준비합니다.
4
연결 복원저장된 연결 메타데이터와 OS 비밀 파일을 사용해 Gmail/Slack/HTTP 등을 hydrate합니다.
5
화면·스케줄러·트리거 시작IPC를 등록하고 창을 띄운 뒤 자동 실행 감시를 시작합니다.

종료할 때

1
새 실행 받지 않기Scheduler와 TriggerEngine을 멈춥니다.
2
진행 중 실행 기다리기Runtime이 in-flight 작업을 끝낼 때까지 기다립니다.
3
DB flush대기 중인 저장 타이머를 처리하고 DB 파일을 닫습니다.
그래서 PC를 강제로 끄거나 프로세스를 죽이면 “마지막 몇백 ms의 저장”은 별도 복구 설계가 필요합니다. 중요한 데이터는 앱 종료만 믿지 말고 백업 경로를 마련해야 합니다.

8. 지금 개발자가 특히 확인할 것

아래는 “당장 전부 뜯어고치라”는 뜻이 아니라, 완성본을 목표로 할 때 우선순위를 잡기 위한 현재 코드 관찰입니다.

상태관찰왜 중요한가다음 확인
현재 확인됨 이 설명서를 만드는 시점의 Core TypeScript 검사는 통과했습니다. 다만 작업 트리가 계속 바뀌므로 test/build를 함께 반복 확인해야 합니다. 타입 검사 하나만 통과해도 실제 테스트·번들·문서 엔진 연결까지 정상이라는 뜻은 아닙니다. Core test/typecheck/build를 같은 기준으로 실행하고 결과를 기록
운영 설계 실행 로그는 log_json 배열 전체를 계속 다시 저장하고, 실행/trigger receipt의 자동 보관 기간은 아직 명확하지 않습니다. 실행이 쌓이면 DB 파일과 메모리, 백업 크기가 계속 커질 수 있습니다. 보관 기간·최대 크기·압축·아카이브 정책을 명시하고 테스트
장애 복구 trigger_receipts가 processing일 때 앱이 죽으면 다음 실행에서 영원히 재시도하지 않을 가능성이 있습니다. 외부 이벤트를 놓치거나, 반대로 중복 실행을 막는 과정에서 멈출 수 있습니다. lease/timeout/heartbeat와 “재처리 가능 상태”를 설계
로컬 앱 한계 기본 구조는 한 PC의 단일 사용자 로컬 앱입니다. 여러 사용자가 같은 실행 큐와 DB를 공유하는 서버 구조는 아닙니다. 팀 협업, 중앙 실행, 24시간 무인 운영을 원하면 별도 서버/큐/권한 모델이 필요합니다. 제품 목표를 “개인 데스크톱”인지 “팀용 서비스”인지 먼저 확정
DB 진화 테이블 생성과 일부 legacy rename은 있지만, DB 스키마 버전표와 단계별 migration 기록은 별도 체계로 더 다듬을 필요가 있습니다. 필드 추가·변경이 반복되면 사용자 DB를 안전하게 업그레이드하기 어려워집니다. schema version, forward migration, rollback/backup 검증을 도입
실행 환경 현재 개발 환경에서는 native better-sqlite3가 로드되지 않아 sql.js fallback으로 테스트되었습니다. 개발·테스트·배포에서 DB 성능과 파일 잠금·동시성 특성이 달라질 수 있습니다. 배포 이미지에서 native binding 설치를 검증하고, fallback도 의도된 지원 경로인지 결정
잘 잡힌 부분 context isolation, nodeIntegration 비활성화, sandbox, IPC sender 검증, JSON 스키마 검증이 들어가 있습니다. 화면이 곧바로 OS 파일·토큰·Node 권한을 갖지 않도록 경계를 둔 것입니다. 이 경계를 깨는 새 IPC가 생길 때마다 회귀 테스트 유지
이번 확인 결과: Core typecheck, Core build, Core 전체 테스트(87개 파일·409개 테스트), eval(11개)이 통과했습니다. 단, 테스트는 native DB가 아닌 sql.js fallback 환경이었다는 점을 함께 기록해야 합니다.
개발 순서 제안: 위 초록색 기준을 계속 유지하고, 그 다음 “워크플로 저장 → 앱 재시작 → 다시 읽기 → 실행 → 승인 재개 → 이벤트 중복 방지”를 하나의 통합 시나리오로 자동 테스트하는 것이 가장 효과적입니다.

9. 기억할 것

무엇인가?

Electron 기반 로컬 자동화 앱이며, Main/Core가 백엔드 역할을 합니다.

어떻게 작동하나?

화면 요청을 IPC로 넘기고, Core가 검증한 WorkflowIR을 Runtime과 Connector로 실행합니다.

왜 중요한가?

기능을 추가할 때 화면만 고치는 것이 아니라 실행·저장·재시작·장애 복구까지 함께 설계해야 하기 때문입니다.

개발자용 한 줄: “이 버튼이 어느 IPC를 타고, 어떤 Core 함수가 받고, 어떤 repository가 어떤 JSON을 어느 저장소에 쓰며, 앱이 재시작되었을 때 같은 상태를 복구할 수 있는가?”를 기능마다 답할 수 있으면 백엔드 흐름을 제대로 이해한 것입니다.
최소 용어집
RendererReact 화면 프로세스. 사용자가 보는 UI.
MainElectron의 권한 있는 프로세스. 창, 파일, OS 기능, IPC를 관리.
